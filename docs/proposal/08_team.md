## 8.2 职责边界

【判断】分工的第一原则是**不重叠**。本节把责任写成「谁负责、具体做什么、交付物是什么、与谁交接」，避免出现「大家一起做A」这种在答辩时无法回答的分工。

### 角色 1：负责人（兼算法与检索）

| 项 | 内容 |
| --- | --- |
| **责任范围** | 赛项确认与报名推进、里程碑与砍量决策、检索与诊断链路（`loweye/retrieval/`、`loweye/parsing/`）、评测口径与 `out/eval_report.md`、答辩主答 |
| **具体做什么** | ① 维护评测集与指标口径；② 推进检索后端替换（BGE-M3 + bge-reranker-v2-m3）并复测留出集；③ 维护分级规则表 `config/routes.yaml` 与三道范围闸门；④ 对「可溯源率」「引用可核验率」这类结论签字负责 |
| **交付物** | 评测报告（含五配置对照与分组指标）、检索后端替换前后的对照表、方案书第二、三、四章 |

## 8.3 为什么 3 人以内能做完

### 8.3.1 工作量估算

【事实】本项目已经产出的规模（不含方案书）：

| 部分 | 规模 |
| --- | --- |
| 后端 `loweye/` | 40 个 Python 文件，4324 行 |
| 前端 `web/` | 3 个文件，1958 行 |
| 工具 `tools/` | 10 个脚本，1131 行 |
| 测试 `tests/` | 9 个文件，778 行 |
| 配置与模板 | `config/` 下 4 个文件 |
| 评测集 | `eval/gold_qa.yaml` 64 题 |
| 合计代码 | **约 8200 行** |

【判断】按 3 人 × 8–12 小时/周 × 约 28 周（2026-10 中旬至 2027-04 下旬）估算，总投入约 670–1000 人时。当前约 8200 行代码若按 15–25 行/人时的实际产出效率（含调试、返工、文档），对应约 330–550 人时；余下的 300–500 人时用于补齐短板（真实权重、评测复测、标注集、盲评）与材料撰写。**这个估算是一个判断，不是实测，误差方向是低估而非高估**（原因是真实数据集接入与权重训练的不确定性高于编码本身）。

### 8.3.2 三个结构性原因

1. **架构不依赖多人并行**。【事实】编排层是显式状态机，没有引入多 Agent 框架，模块边界（识别 / 诊断 / 编排 / 派单报告 / 控制台 / 评估）与目录一一对应，单人可以在一天内改完一条链路。
2. **演示路径短**。【事实】免构建、无第三方运行时依赖、断网可跑；演示只需一条命令启动，不需要构建产物或容器编排。
3. **技术上不做大模型训练**。【事实】本项目不训练大模型，生成走模板或云端 API，重排与嵌入用开源权重推理。因此不需要数据工程团队与大规模算力，避免了「人不够→模型训不出来→全盘延期」的传导链。

### 8.3.3 三人以内的主要风险与提前约束

【判断】风险不在工作量，而在**关键人失效**：本项目目前的知识集中在检索与编排这两条链路上。

| 约束 | 做法 |
| --- | --- |
| 关键人休假/考试周 | 每两周一次 30 分钟交接，任何人能跑通 `api_smoke.py` 与 `tools\reset_demo.py` |
| 环境不可复现 | 固定 `.venv`、固定端口 8848、固定演示图清单，环境搭建步骤写进 README |
| 材料最后一周才开始 | 材料从 2027-01 起并行推进，不等实验全部结束（见第九章 9.1 的 ML-06 与 9.4 的砍量规则） |
| 单一成员承担全部写作 | 每章有明确的第一作者，负责人只做口径终审 |

## 8.4 外部支持需求

【判断】外部支持的作用是**补资源与补视角**，不是补人力。以下需求按优先级排列，其中「是否需要」与「能否获得」均待确认。

### 8.4.1 指导教师

| 需要什么 | 为什么需要 | 状态 |
| --- | --- | --- |
| 赛事流程与报名指导 | 校内审核、材料格式、时间节点的官方口径 | 【待填：是否已有指导教师】 |
| 规程来源与业务口径 | 真实 GB/DL/T 文档的获取途径；分级与时限的实际执行口径 | 【待填】 |
| 材料评阅 | 在提交前给出结构与表述意见 | 【待填】 |
| 行业联系 | 争取一次一线巡检人员访谈或一份匿名历史缺陷图 | 【待填】 |

【判断】需要明确边界：指导教师提供方向、资源与评审，**不代写代码、不代写材料**。

### 8.4.2 学校竞赛管理部门

报名由学校统一组织，需校内审核，因此需要：报名编号与官方通知、校内截止时间（**可能早于赛项截止日**）、盖章材料的办理流程。【待核实】校内截止时间未取得，需以本校通知为准。

### 8.4.3 实验室机器与数据

| 需求 | 用途 | 状态 |
| --- | --- | --- |
| 具备 NVIDIA 显卡（建议 ≥8GB 显存）的机器 | 检测权重训练与导出；BGE-M3 与重排模型的一次性编码 | **【待填：是否有 8GB 显存机器】** |
| 可长期在线的机器 | 手机/公网演示时需要主机在线 | 【待填】 |

### 8.4.4 团队之外的人员

| 需求 | 数量与构成 | 用途 |
| --- | --- | --- |
| 盲评人 | ≥3 位非本组成员，含 1 位非工科背景、1 位行业背景 | 去偏与可用性反馈（回收 ≥4 份） |
| 一线视角 | 1 位巡检/植保/应急岗位从业者 | 校验分级与时限是否符合实际 |

## 8.5 三种团队规模下的合并方案

| 规模 | 分工安排 | 主要影响 |
| --- | --- | --- |
| **3 人**（理想） | 8.2 的三个角色各担其一 | 材料与实验可并行，风险最低 |
| **2 人** | 角色 1 保留；角色 2 与角色 3 合并 | 材料撰写与前端演示争抢同一人时间，需要在 2027-02 后降低代码改动频率 |
| **1 人** | 三角色全部由一人承担 | 必须先执行砍量规则：砍扩展场景、砍大屏、砍 SAHI、砍报告导出与 webhook；只保留检测闭环、条款级溯源、三基线对照、商业与市场章 |

【判断】「不得砍」的四项（检测闭环、条款级溯源、三基线对照与人效对比、商业/市场/ROI 章）在任何规模下都不砍。单人规模下，方案书篇幅也应相应压缩，而不是把 3 人的工作量原样堆给 1 人。
