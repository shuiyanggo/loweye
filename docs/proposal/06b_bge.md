# 第五章附　换 BGE 后端后的复测（第九章 ML-03 里程碑结果）

> 本章是全篇唯一一次「里程碑达标性复测」。第九章把 **留出集 Recall@1 ≥ 80%** 列为唯一一个「不达标就要改变方案书主张」的里程碑（ML-03），因为第五章创新点一的成立方式直接依赖它。本章给出改造后的实测结果、代价，以及过程中发现并修掉的两个会让「拒答」静默失效的缺陷。

## 附 1 改了什么

| 项 | 默认词法档 | BGE 档 |
| --- | --- | --- |
| 向量后端 | `hashing_tfidf`（特征哈希 + IDF，4096 维，纯 numpy） | `BAAI/bge-m3`（1024 维，本地权重 `models/bge-m3`） |
| 重排后端 | `lexical`（条款号命中 + 词覆盖 + 字级重合，绝对分） | `BAAI/bge-reranker-v2-m3`（cross-encoder，logits 经 sigmoid 得绝对分） |
| 配置 | `config/app.yaml` | `config/app.bge.yaml`（独立文件） |
| 索引 | `data/index` | `data/index_bge`（独立目录，互不覆盖） |

两档共用同一套金标集（`eval/gold_qa.yaml`，34 字面 + 12 改写开发集 + 10 留出 + 8 越界）、同一套指标、同一个评测脚本。留出集是在词法档的术语表冻结之后才写的，此前未参与任何调参。【事实】

顺带改了候选集构造：原实现在融合阶段只取 RRF 前 20 名作为重排候选，实测换语义向量后有硬伤——留出题的正确答案常出现在向量通道第 1~8 名，却被 BM25 的强命中用 RRF 名次压出候选集，重排再强也救不回来（留出题 Recall@1 从向量单路的 8/10 掉到 RRF 的 4/10）。现改为**两路召回取并集，按「两路中较好的名次」排序后取前 `fused_top_k`**，RRF 分仍照算，只用于展示与同分打平。【实测】

## 附 2 全量对照（56 道域内题）

| 配置 | 词法档 Recall@1 / MRR | BGE 档 Recall@1 / MRR |
| --- | --- | --- |
| 仅 BM25 | 82% / 0.861 | 82% / 0.861 |
| 仅向量 | 86% / 0.898 | 88% / 0.935 |
| RRF 融合（无重排） | 86% / 0.893 | 80% / 0.882 |
| **融合 + 重排（本系统）** | **89% / 0.917** | **95% / 0.973** |
| 融合 + 重排（关闭术语表） | 79% / 0.814 | 93% / 0.955 |

BM25 一路两档完全相同（同一份 `rank_bm25`、同一套分词），这正是对照实验要的效果：差异全部来自向量与重排两路。【事实】

## 附 3 分组对照与 ML-03 结论

| 分组 | n | 词法档 Recall@1 / MRR | BGE 档 Recall@1 / MRR |
| --- | --- | --- | --- |
| 字面题 | 34 | 100% / 1.000 | 100% / 1.000 |
| 改写题（开发集，术语表在此开发） | 12 | 92% / 0.926 | 83% / 0.917 |
| **留出题（未参与任何调参）** | 10 | **50% / 0.625** | **90% / 0.950** |
| 越界拒答（8 题） | 8 | 100% | 100% |

**ML-03 达标：留出集 Recall@1 从 50% 提升到 90%**（10 题里答对 9 题，仍有 1 题错，不是满分）。【实测】

三条必须一起读的限定：

1. **改写题（开发集）反而从 92% 掉到 83%。** 这一组是术语表的开发集，词法档在这组上是「练过的」，而 BGE 档全程没有针对它调参。只报留出集会显得全面提升，只报开发集会显得改造失败——两组必须并排给。【判断】
2. **代价是时延。** 检索 P50 从 4.1 ms 涨到 2524 ms、P95 从 5.08 ms 涨到 2956 ms；端到端 P50 从 9.18 ms 涨到 3864 ms、P95 从 25.56 ms 涨到 5202 ms（n 分别为 168 / 8，本机 CPU、无 GPU）。瓶颈是 cross-encoder 给每题 20 个候选逐对打分。因此 BGE 档定位是**离线批处理与答辩对照**，现场逐张实拍演示仍走词法档；要用于产线需要 GPU、更小的重排模型或量化 ONNX。【实测】
3. **知识库仍是自编占位文档。** 本章所有数字证明的是「检索策略在留出说法上的泛化能力」，不是「在真实规程上的准确率」；换成真实标准原文后必须重测。【事实】

## 附 4 过程中修掉的两个缺陷（都会让拒答静默失效）

**缺陷一：交叉编码器被套了两层 sigmoid。** `sentence-transformers` 的 `CrossEncoder` 在 `num_labels=1` 时默认已套一层 Sigmoid，而项目代码里又套了一层，分数被压到 0.5 附近——实测域内题 0.5079~0.7309、域外题 0.5000~0.6557，两组几乎重叠，`min_relevance = 0.18` 形同虚设：**越界拒答率从 100% 掉到 38%**。修法是显式传 `activation_fn=torch.nn.Identity()`，激活只由本项目套一层。修完后同一批题：域内样例 0.9874、边界题 0.1344、完全无关题 0.0010，分数彻底分开。【实测】

**缺陷二：范围排除闸门判在重排后的第一名。** 原实现只看重排第一名是不是「本导则不适用于……」，而 BGE 重排会把这类排除声明从第 1 名挤到第 2、3 名，闸门随之失效。现改为**在召回阶段（BM25 与向量的并集）前 3 名里判**：召回衡量的是主题相近，重排衡量的是「这条能不能当答案」，两者不是一回事。【判断】

两个缺陷都写在代码注释里，并各留了边界题的回归用例。它们也是本方案坚持「拒答是一等公民」的原因：**换更强的模型不会自动让拒答变好，反而可能把拒答一起换掉——所以拒答率必须和召回率一起测。**【判断】

## 附 5 复现

```powershell
# 1) 拉权重到项目内（默认走 ModelScope 镜像；huggingface.co 直连不通）
.venv\Scripts\python.exe -m tools.fetch_models --source ms

# 2) 独立索引 + 独立评测
.venv\Scripts\python.exe -m loweye.cli.build_kb --config config/app.bge.yaml
.venv\Scripts\python.exe -m loweye.cli.evaluate --config config/app.bge.yaml `
  --report out/eval_report_bge.md --json out/eval_report_bge.json

# 3) 两档对照表（指标从行级排名现场重算，不抄小结数字）
.venv\Scripts\python.exe -m tools.eval_compare --a out/eval_report.json --b out/eval_report_bge.json
```

本机实测开销（用于答辩时回答「CPU 跑不跑得动」）：`bge-m3` 加载 2.0 s、68 条条款全量编码 7.0 s（9.7 条/秒）、单条查询编码 68 ms，向量维度 1024；两个 2 GB 级模型同时常驻约需 5 GB 可用内存。【实测】
