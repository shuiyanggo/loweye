# 第一章 项目概述

## 1.0 本章的标注规则

与第七章一致，本章每一条陈述都标注性质，不混用：

| 标注 | 含义 |
| --- | --- |
| 【事实】 | 可被第三方复核的客观信息（赛事规则、代码与配置现状、外部公开信息） |
| 【实测】 | 本项目在本机跑出的数字，给出测试条件 |
| 【目标】 | 尚未达成、写进里程碑的指标 |
| 【待核实】 | 来源不够硬或尚未取得官方原文，不得当作结论使用 |
| 【判断】 | 团队主观观点 |

本章不使用「行业领先」「填补空白」这类无法量化的表述。

## 1.1 一句话定位

> **低空之眼是一套低空巡检决策层软件：把无人机拍回来的巡检图，变成一张带规程条款出处的可执行工单。它不造无人机、不做飞控、不卖硬件。**

输入是一张巡检图，输出是六件事：检出什么缺陷 → 判几级 → 依据哪一条规程 → 派给谁 → 多少小时内到场 → 谁来复核。每一步都强制回带条款号，知识库没有覆盖时**明确拒答**，不编一段听起来合理的话。【事实】

---

## 1.2 要解决的真实问题

### 1.2.1 瓶颈已经从「拍不到」移到「判不完」

无人机把图像拍回来的环节已经基本解决，判读这些图像的环节还停在人工状态。【判断】

可从公开信息看到的量级：

- 国家电网 110 千伏及以上输电线路达 131 万公里，投入近 4 万台无人机，年智能巡检杆塔 1000 万基。【事实】来源：人民日报《「人工智能+」，央企咋布局？》（2025-04-02 第 18 版，经 CPEM 转载，http://huiyi.cpem.org.cn/epcmd/list/5260.html）
- 同篇报道给出的「减少人工登塔 40%、巡视效率提升 2 倍以上」是**飞行层**的贡献，不是本项目的贡献。本项目压缩的是图像拍回来之后的人工环节。【判断】

### 1.2.2 一个缺陷从「被看到」到「被处置」之间，隔着四个问题

巡检员看到图上一个缺陷之后，必须回答四个问题，而这四个问题的答案都不在图里：

| 问题 | 答案在哪里 | 现状 |
| --- | --- | --- |
| 判什么级（危急／严重／一般） | 缺陷定级标准、运检规程 | 靠人翻规程、凭经验 |
| 派给谁（哪个班组、哪个岗位） | 本单位职责划分 | 靠人对人喊话、微信群 |
| 多久内处置（SLA） | 规程时限条款 | 靠记忆，超期了才发现 |
| 依据哪一条 | 规程条款号与原文 | 通常不留痕；留痕也是「按规程要求」 |

【判断】这四个问题的共同点是：**它们的答案不在图像里，而在文本里。** 因此单纯提高检测精度解决不了这一段——检测器再准，也只会更准确地告诉你「这里有一个绝缘子自爆」，不会告诉你它对应危急缺陷、24 小时内、输电运检班、依据 2.1.2 条。

### 1.2.3 这一段的错误有真实的后果

- 判轻了：该停电处理的缺陷按一般缺陷排期，缺陷继续发展。
- 判重了：把不适用当前条件的条款照搬过来，造成一次不必要的停电。本项目的条件分支闸门就是为这一类错误设的——金具锈蚀不会照搬「出现裂纹、变形或磨损的，应按危急缺陷流程处理，立即申请停电更换」。【事实】
- 查不到依据：工单归档时说不清为什么这么派，事后追责没有落点。

【判断】在电网运检场景里，「可复现、可追责」本身就是需求，不是附加项。一个每次给出不同条款的生成式系统，在这个场景里是减分项，不是加分项。

## 1.3 本项目在链条中的位置：决策层

低空巡检的完整链条与各环节的责任方：

| 层 | 做什么 | 代表参与者 | 本项目 |
| --- | --- | --- | --- |
| 飞行层 | 机体、飞控、机场、航线、空域申请 | 无人机厂商、巡检服务商 | **不做** |
| 采集层 | 可见光／红外载荷、影像回传、拼接建模 | 无人机厂商、测绘软件 | **不做** |
| 识别层 | 从图像中检出缺陷目标 | 视觉算法厂商、开源模型 | **做，但不是重点**（见 1.4） |
| **决策层** | **缺陷 → 严重度 → 规程条款 → 处置动作 → 工单 → 复核 → 报告** | **本项目** | **核心** |
| 执行层 | 停电、检修、砍伐、施药 | 运检班组、植保服务队 | **不做**（只派单与跟踪） |

【事实】本项目代码仓库中不含任何飞行控制、航迹规划、硬件驱动相关模块；检测模块（`loweye/detect/`）只负责从图像出框，不做飞行决策。

**为什么选决策层，而不是识别层或飞行层**（【判断】，三条理由）：

1. 飞行层是重资产，学生团队在比赛窗口内不可能做出可演示的机体与飞控。
2. 识别层已经高度商品化，且必须靠数据与算力取胜——本项目没有这两样（见 1.6 短板一）。
3. 决策层的判据是**文本**而不是像素：规程条款、时限、职责边界。它的难点是工程化与可审计性，而不是模型规模，这一点与学生团队的能力结构相匹配。

## 1.4 与「又一个缺陷检测模型」的区别

**【判断】本项目不以检测精度作为主要论点。** 理由不是检测不重要，而是：

1. 检测精度在本项目当前状态下属短板（演示检测读的是 sidecar 标注，没有真实权重），把它当主论点必然翻不回来。
2. 检测精度是**别人更容易赢的维度**：公开数据集、开源权重、算力这三样，任何一家厂商都比学生团队多。
3. 检测精度本身不产生工单。一个 0.95 mAP 的检测器与一个 0.90 mAP 的检测器，在「这张工单能不能被签批」这件事上没有区别。

**真正的差别在「动作能不能落地」与「依据能不能核对」。** 本项目用同一批样本做了三组对照（每个「图片 × 缺陷类别」算一个样本，三组共用同一判据）。【实测】

| 组 | 做法 | 给出处置动作比例 | 可溯源率（动作带条款号） | 引用可核验率 |
| --- | --- | --- | --- | --- |
| A 纯检测 | 只报缺陷框 | 0% | 0% | — |
| B 直接问多模态大模型（无知识库） | 直答 | 100% | **0%** | — |
| C 本系统 | 检索规程条款后生成 | 100% | **100%** | **100%**（逐字回查全部引用） |

必须说明三件事，否则这张表会被读成吹牛：

- 「给出处置动作比例」三组共用同一个判据（`is_actionable`），B 组说的话同样「像建议」，**因此这一列不构成质量优势**。【事实】
- A、B 两组结构上就不可能带条款号，可溯源率天然为 0，不是它们做得差。【事实】
- B 组默认走脚本化代理（`arm_b_mode: scripted`），代表「一个不做检索直答的模型」的结构特征，**不代表某个具体模型的真实水平**。【事实】

**一句话的区别**：别人的系统告诉你「这里有缺陷」，低空之眼告诉你「这里有一个危急缺陷，依据 2.1.2 条，24 小时内派输电运检班，P1 需人工确认后派单」。【判断】

## 1.5 项目边界：明确不做什么

| 不做 | 原因 |
| --- | --- |
| **不造无人机、不做飞控、不卖硬件** | 团队无此能力，且与决策层定位无冲突 |
| 不训练通用大模型 | 无算力、无数据，且不是本项目的价值所在 |
| 不做底层算法创新（新检测结构、新检索算法） | 本项目的创新点在链路组织与可审计性，不在算子级 |
| **分级不交给大模型判断** | 分级直接决定派单与时限，必须可复现、可审计，用确定性规则表（`config/routes.yaml`） |
| 不允许无依据生成处置建议 | 知识库没覆盖就说不覆盖，分「分数不够」与「明确排除」两种拒答 |
| 不在合成演示图上宣称检测精度 | 演示图为程序化合成图，标注为同名 sidecar，属于自证循环（见 1.6 短板一） |
| 不主张预测性维护、寿命评估、故障预测 | 需要长周期运行数据，本项目无此数据 |
| 红外双光融合 | 当前无数据无方案，已从架构图中删除；要恢复需先补一份红外电力数据 |

【判断】把「不做什么」写在最前面，是因为作品赛的评审会按方案书里画出的每一块去追问实现。画了不做的部分，是确定的失分点；明确划掉的部分，反而是可信度的来源。

## 1.6 当前完成度与四条短板

### 1.6.1 已跑通并实测

以下数字全部来自仓库内脚本，命令见 README 第三节；口径声明见 README 第七节第 4 小节与 `out/eval_report.md` 第 1 节。【实测】

| 维度 | 现状 |
| --- | --- |
| 知识库 | 3 篇文档 → **68 个条款块，带条款号 65 块（95.6%）** |
| 检索（56 题金标集，域内题） | Recall@1 **89%** / Recall@3 93% / Recall@5 95%，MRR **0.919** |
| 检索（留出集 10 题，术语表定稿后才写） | Recall@1 **50%** / MRR 0.637（**这一组才是对「没见过的说法」的真实表现**） |

| 端到端链路 | 单图 → 检测 → 诊断 → 分级派单 → 工单落盘 → HTML/PDF 报告，4 张演示图全部跑通 |

| Web 控制台 | 4 个页签（分析台 / 工单 / 知识库 / 追溯），免构建、无第三方运行时依赖、**断网可跑** |
| 单元测试 | 106 项全绿（`unittest`，标准库）。**注：`unittest discover` 实测收集到 118 项，README 与命令行注释两处数字不一致，定稿前需核实以哪一处为准。**【待核实】 |

**知识库规模为 68 个条款块、检索指标取自 3 篇自编占位文档**，与真实规程语料的规模不在一个量级。【事实】

### 1.6.2 四条短板（照抄 README 口径，不美化）

**短板一：检测用的是 sidecar 标注，不是真实模型。**

演示图的检测框读自同名 `.detections.json`，用于验证链路连通性；真实模型接口（ONNX + SAHI 切片）代码已就位，但**没有权重**。因此本项目**不提供任何检测精度结论**。【事实】

**短板二：检索后端是词法实现，不是语义模型。**

当前为 BM25（`rank_bm25`）+ hashing_tfidf（dim=4096）+ 词法重排 + 领域术语表。留出集上 Recall@1 只有 **50%**，**这是当前最大的技术短板**；替换方案明确（BGE-M3 向量 + bge-reranker-v2-m3 重排）。【事实】

**短板三：知识库是自编占位文档。**

3 份演示用规程为项目自编文本，不是真实 GB/DL/T 标准原文。检索指标反映的是**检索策略的相对差异**，不代表在真实规程上的表现。【事实】

**短板四：通知与天气工具默认关闭。**

钉钉／飞书 webhook 与和风天气需要配置环境变量后才可用，默认关闭；它们依赖公网，不进入离线演示的关键路径。【事实】

### 1.6.3 四条短板对结论的约束

【判断】以上四条决定了：**本方案书不能把检索指标与链路完整度写成系统在真实规程上的能力。** 当前可主张的只有两件事：

1. 这条链路（识别 → 诊断 → 分级 → 派单 → 复核 → 报告）是**跑通的**，不是设计稿；
2. 「可溯源」与「可拒答」是**结构上**成立的（引用强制回带条款号、无覆盖即拒答），不依赖模型精度。

至于「在真实规程上有多准」，必须等短板一、二、三补齐后重测。这是本项目在答辩与方案书中最需要守住的口径。【判断】

## 1.7 本章结论

1. **定位**：低空之眼是低空巡检的决策层软件，把图像变成带条款出处的可执行工单，不碰飞行与硬件。【事实】
2. **真问题**：瓶颈已从「拍不到」移到「判不完」；缺陷到处置之间的四个问题（判什么级、派给谁、多久内、依据哪条）的答案都在文本里，不在图像里。【判断】
3. **差异化**：不以检测精度为主论点，差别在可溯源率与引用可核验率（三组对照：0% / 0% / 100%）。【实测】
4. **边界**：不造无人机、不做飞控、不做底层算法创新、分级不交给大模型、无依据不生成建议。【事实】
5. **完成度**：链路跑通、可复现、指标实测；但检测无权重、检索为词法实现（留出集 Recall@1 50%）、知识库为自编占位文档。【事实】
6. **后续章节的诚实前提**：在真实规程语料与真实检测权重上重测之前，本项目的精度类主张一律以待验证区间表述，不作承诺。【判断】
