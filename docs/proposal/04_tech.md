## 4.1 四层架构

### 4.1.1 分层原则

本项目的分层不是概念图，而是目录与依赖方向的一一对应：**上层可以调用下层，下层不知道上层存在**。【事实】

| 层 | 职责 | 对应目录/文件 | 依赖方向 |
| --- | --- | --- | --- |
| 数据层 | 阈值、规则、术语、知识文档、索引、金标集 | `config/`（5 个文件）、`data/raw → data/processed → data/index`、`eval/gold_qa.yaml`、`data/assets` | 被所有层读取，不依赖任何业务代码 |
| 能力层 | 四个可替换的后端能力：切分、检索、检测、生成 | `loweye/parsing/`、`loweye/retrieval/`、`loweye/detect/`、`loweye/llm/` | 只依赖数据层与 `loweye/schemas.py` |
| 编排层 | 把能力串成一条有状态、有降级、有时序的流程 | `loweye/agent/pipeline.py`、`loweye/agent/grading.py`、`loweye/agent/tools.py` | 依赖能力层 |
| 应用层 | 对外呈现与交付：接口、控制台、命令行、产物 | `loweye/api.py`、`web/`、`loweye/cli/`、`tools/`、`out/` | 只依赖编排层暴露的结构化结果 |

【事实】后端共 40 个 Python 文件、4324 行（README 第四节）；前端 3 个文件、1958 行；开发与演示脚本 10 个、1131 行；单元测试 9 个文件、778 行。

### 4.1.2 数据层：配置即接口

| 文件 | 内容 | 关键点 |
| --- | --- | --- |
| `config/app.yaml` | 全局配置（104 行） | 检索 top-k 与阈值、检测后端与切片参数、生成后端、工具开关、评测模式、服务端口 |
| `config/routes.yaml` | 分级派单规则表（81 行） | 10 条缺陷规则 + 4 个人工复核触发条件；文件头写明「分级不交给大模型判断」 |
| `config/lexicon.yaml` | 领域术语表（106 行，47 条） | 口语说法 → 规程术语，检索前归一化并追加规范术语 |
| `config/sources.yaml` | 知识文档登记 | 每份文档带 `source_version` 与来源性质；演示文档标为「项目自编占位文本」 |
| `config/report_template.html` | 报告模板（Jinja2） | 交给 PyMuPDF Story 排版，同一份模板出 HTML 与 PDF |
| `eval/gold_qa.yaml` | 金标问答集 64 题 | 34 原词 + 12 改写（开发集）+ 10 改写（留出集）+ 8 越界 |

【判断】把阈值放进配置文件而不是代码常量，带来的不是「可配置」这个卖点，而是**可审计**：答辩现场要解释「为什么拒答」，答案是打开 `app.yaml` 指一行，不是回顾某个函数里的字面量。

### 4.1.3 能力层：四个可插拔后端

每一类能力都定义了统一的 Protocol，并至少提供「零下载的默认实现」与「装了依赖才可用的增强实现」，两者接口一致，可跑同一套评测脚本做对照。【事实】

| 能力 | 默认（零下载） | 增强（需额外依赖） | 降级方向 |
| --- | --- | --- | --- |
| 文档切分 | 内置「章-节-条」语义切分（`loweye/parsing/`） | — | — |
| 向量召回 | `hashing_tfidf`（dim=4096） | `sentence_transformer`（BAAI/bge-m3） | 增强 → 默认 |
| 词法召回 | `rank_bm25` | — | — |
| 重排 | `lexical`（确定性词法重排） | `cross_encoder`（BAAI/bge-reranker-v2-m3） | 增强 → 默认 |
| 检测 | `sidecar`（读同名 `.detections.json`） | `onnx`（需权重） | 增强 → sidecar → 空检测器 |
| 生成 | `template`（从条款确定性拼装） | `openai_compat`（OpenAI 兼容接口） | 增强 → 模板 |

【事实】`hashing_tfidf` 的特征是「词级 token + 字级 2~3 gram」两类拼接，用 blake2b 哈希到 4096 维，权重取 `(1 + log tf) × idf`（`idf = log((1+N)/(1+df)) + 1`），最后逐行 L2 归一化，因此点积即余弦。它是纯 numpy 实现，零下载、零显存、结果确定。它的模块 docstring 明确声明「它不是神经网络嵌入」——本项目不把它当语义模型宣传。【事实】

### 4.1.4 编排层与应用层

编排层是本项目唯一「知道整条业务」的地方：状态、时序、降级、归档都在 `loweye/agent/pipeline.py`（376 行）里，不引入 LangChain 之类的 Agent 框架。【事实】

应用层对外只暴露结构化结果（Pydantic v2 契约集中在 `loweye/schemas.py`），前端与评测脚本读**同一份契约**。【事实】这一点写在 `loweye/api.py:3-6` 的接口设计原则里，三条是：每个接口有明确响应模型；任何一步降级都出现在 `degradations` 里，不吞异常、不返回「看起来正常」的假结果；提供 `/api/selfcheck` 一键跑通全链路并返回逐步耗时。

### 4.1.5 数据流

```
图片 ──▶ M1 识别 ──▶ M2 检索(诊断) ──▶ M3 编排(分级·派单) ──▶ M4 报告/工单 ──▶ M5 Web 控制台
           │              │                    │                    │
           └──────────────┴────────────────────┴────────────────────┘
                                  M6 评估与观测（贯穿）
```

（出处：README 第五节）

## 4.3 三个决定架构形态的选择

### 4.3.1 编排写成显式状态机，而不是 ReAct 循环

【判断】本项目在编排层做的第一个取舍是：**不引入 ReAct 循环，不引入多 Agent 框架。** 四条理由，按重要性排序：

1. **流程是确定的，让模型决定下一步只会引入不确定性。** 从一张图到一张工单的顺序不存在分支歧义：先检测、再检索、再分级、再派单、最后归档。ReAct 式循环在这个流程里能「自由决定」的部分，恰好是**不该由模型决定**的部分——比如要不要跳过检索直接给建议。【判断】
2. **状态机可以在答辩现场逐行解释。** `pipeline.py` 的阶段键是固定的四个：`detect`、`diagnose`、`grade_dispatch`、`archive`（`loweye/agent/pipeline.py:160`、`:262`、`:301`、`:316`），业务上对应「识别 → 诊断 → 分级 → 派单 → 归档」五步（分级与派单在同一阶段内完成）。每一步的耗时、降级、产物都能单独拿出来看。【事实】
3. **降级链需要一个固定的挂载点。** 本项目的降级不是异常处理，而是**结果的一部分**：`Degradation(stage=..., reason=..., fallback=...)` 三字段结构化记录，随结果一起返回、一起归档、一起出现在报告里。降级阶段名是枚举的：`bootstrap`、`detect`、`retrieve`、`generate`、`dispatch`、`notify`（`loweye/agent/pipeline.py:150-152`、`:162`、`:200`、`:238`、`:292`、`:299`）。在一个自由循环里，这些挂载点无处安放。【事实】
4. **依赖成本。** 引入 Agent 框架会把「40 个文件、4324 行」的项目推向一个需要学习框架、锁定版本、排查框架内部行为的规模，而本项目是 1–3 人的学生团队（见第八章）。【判断】

**这不是说 ReAct 无用**，而是说它解决的问题（开放式任务里「下一步做什么」不确定）在本项目里不存在。本项目里真正不确定的是「这段话对应哪一条规程」——那一部分交给检索，不交给循环。【判断】

### 4.3.2 分级用确定性 YAML 规则表，不让模型判断

【事实】`config/routes.yaml` 的文件头原文：「分级不交给大模型判断，用确定性规则表。理由是分级直接决定派单与 SLA，必须可复现、可审计、可在答辩现场逐条解释。处置动作（actions）不写死在这里，而是由知识库检索结果 + 模板生成，保证每条动作都能回带条款号（可溯源）。」

规则表结构（`config/routes.yaml:8-73`）：默认值 `severity: P3`、`assignee_role: 运维班组`、`sla_hours: 72`，加 10 条缺陷规则：

| 规则键 | 标签 | 等级 | 时限 | 责任岗位 |
| --- | --- | --- | --- | --- |
| `insulator_broken` | 绝缘子自爆（伞裙破损） | P1 | 24 h | 输电运检班 |
| `insulator_polluted` | 绝缘子污秽 | P2 | 72 h | 输电运检班 |
| `fitting_corrosion` | 金具锈蚀 | P2 | 72 h | 线路检修班 |
| `conductor_strand_break` | 导地线断股 | P1 | 12 h | 输电运检班 |
| `tower_tilt` | 杆塔倾斜 | P1 | 24 h | 线路检修班 |
| `foreign_object` | 异物悬挂 | P2 | 48 h | 输电运检班 |
| `vegetation_overreach` | 树障超限 | P2 | 120 h | 通道运维班 |
| `crop_disease` | 农作物病害 | P2 | 48 h | 植保服务队 |
| `crop_pest` | 农作物虫害 | P2 | 48 h | 植保服务队 |
| `fire_smoke` | 火情烟雾 | P1 | 2 h | 应急指挥中心 |

【判断】三条理由：

1. **分级的输出是动作，不是文本。** 等级决定派给谁、多少小时内到场。这三个值一旦由模型生成，同一个缺陷两次分析可能得到不同的时限，工单就无法作为承诺发出。【判断】
2. **可复现性在这个场景里是需求，不是加分项。** 电网运检的动作要可追责；一个每次给出不同条款或等级的生成式系统在运检场景里是减分项。【判断】
3. **规则表把「知识」与「模型」解耦。** 换一个省份的规程，改的是 `routes.yaml` 与知识库，不是重训模型。这条也带来一个已知代价：每进一个省份就要重做一次规则与知识库，边际交付成本可能远高于软件本身（该风险见第九章 9.3 风险表）。【判断】

**人工复核是规则的一部分，不是补救措施。** `config/routes.yaml:76-81` 定义四个触发条件：`on_low_confidence`（检测置信度低于 `detect.human_review_threshold`，即 0.60）、`on_no_citation`（检索不到任何条款依据）、`on_severity_in: [P1]`（P1 一律人工确认后再派单）、`on_unknown_class`（检测类别不在规则表内）。**P1 不自动派单**：系统的角色是把依据和选项摆齐，不是替人拍板。【事实】

### 4.3.3 生成默认用模板，因为它在结构上不可能编造条款号

【事实】`config/app.yaml:69-71` 的口径：「生成后端：`template`（默认，从检索到的条款确定性拼装，结构上不可能幻觉）／`openai_compat`（云端或本地 OpenAI 兼容接口）」。

【判断】这里的关键词是**结构上**。模板后端能输出的动作句，只能来自检索命中的条款原文——它没有可以生成新条款号的代码路径。因此「引用一个不存在的条款号」在这条链路上不是「概率很低」，而是**不可达**。这是本项目把「可溯源率 100%」写成结构结论而不是精度结论的原因（对照实验见第六章）。

同时必须说清代价：模板后端的表达灵活性低，长句、跨条款推理、多条件组合的表达都不如模型。当前知识库是自编占位文档、条款句式规整，这个代价还没有暴露；换成真实 GB/DL/T 语料后，模板的可读性会下降，这是 4.3.3 之后要复测的第一件事。【判断】

【事实】增强路径已经写好且接口一致：`openai_compat` 走 OpenAI 兼容接口，配置项为 `base_url`、`api_key_env: LOWEYE_LLM_API_KEY`、`model`、`timeout_s: 20`、`max_retries: 1`。生成失败或超时会**降级回模板**，并把原因写进 `degradations`（`loweye/agent/pipeline.py:198-200`，fallback 文案为「使用 {generator} 生成」）。

## 4.4 检索链路：两路召回 → RRF 融合 → 重排 → top-5

### 4.4.1 链路与参数

| 步骤 | 做什么 | 参数 | 出处 |
| --- | --- | --- | --- |
| 0 查询归一化 | 术语表把口语说法折叠到规程术语，并追加规范术语提高召回 | `retrieval.lexicon: config/lexicon.yaml`（47 条）；置空即关闭（消融对照用） | `config/app.yaml:38-40` |
| 1 词法召回 | BM25 取前 30 | `retrieval.bm25_top_k: 30` | `config/app.yaml:21` |
| 2 向量召回 | hashing_tfidf 余弦相似取前 30 | `retrieval.vector_top_k: 30`、`embed_dim: 4096` | `config/app.yaml:22`、`:31` |
| 3 融合 | RRF（Reciprocal Rank Fusion）按排名融合两路 | `retrieval.rrf_k: 60`、保留前 20 | `config/app.yaml:23`、`:25` |
| 4 重排 | 确定性词法重排，决定最终排序 | `retrieval.reranker: lexical` | `config/app.yaml:36` |
| 5 截断 | 最终取前 5 条进入生成 | `retrieval.final_top_k: 5` | `config/app.yaml:24` |
| 6 覆盖判定 | 最高分低于阈值 → 判「知识库未覆盖」并拒答 | `retrieval.min_relevance: 0.18` | `config/app.yaml:26` |
| 7 引用校验 | 引用必须带出条款号，否则视为不合格引用 | `retrieval.require_clause_no: true` | `config/app.yaml:27` |

【事实】`rrf_k: 60` 的取值理由写在配置文件注释里：「RRF 平滑常数，常用 60」。本项目没有对 k 做扫描调参，采用通行默认值。【事实】

【判断】检索结果是**可分解**的：每个命中的条款同时带着 BM25 分、向量分、RRF 分、重排分四路分数返回。这不是为了界面好看，而是为了在「这条为什么排第一」被追问时能给出机制性回答——如果只有最终名次，调参只能靠试。【判断】

### 4.4.2 为什么两路都要

【实测】评测报告第 2 节的五组配置对照（56 道域内题，MRR）：

| 配置 | Recall@1 | Recall@3 | Recall@5 | MRR | 前 50 命中率 |
| --- | --- | --- | --- | --- | --- |
| 仅 BM25 | 82% | 88% | 91% | 0.861 | 100% |
| 仅向量 | 86% | 93% | 95% | 0.898 | 100% |
| RRF 融合（无重排） | 86% | 93% | 95% | 0.893 | 100% |
| 融合 + 重排（本系统） | 89% | 93% | 95% | 0.919 | 98% |
| 融合 + 重排（关闭术语表） | 79% | 84% | 84% | 0.818 | 93% |

必须同时说明三件事，否则这张表会被读成「融合一定更好」：

- 单看 MRR，**仅向量（0.898）已经高于 RRF 融合（0.893）**。融合的收益出现在加上重排之后（0.919），而不是融合本身。【实测】
- 前 50 命中率上，本系统是 98%，低于仅 BM25 / 仅向量 / RRF 的 100%。也就是说，融合 + 重排在一道题上把正确条款挤出了前 50 名。【实测】本项目没有把这 1 道题挑出来重调，因为重调就等于把评测集变成开发集。
- 术语表的单独贡献很大：关掉它，MRR 从 0.919 掉到 0.818，Recall@1 从 89% 掉到 79%。但术语表的收益**只在它枚举过的说法上成立**，这一点在留出集上暴露得很清楚（6.8 节）。【实测】

## 4.5 三道精度闸门

三道闸门都只作用于「生成处置动作」这条链，**不影响知识库页的自由检索**（那是全库检索）。共同目标是「宁可少答，不可错答」。【事实】

| 闸门 | 拦什么 | 判据来源 | 具体例子 |
| --- | --- | --- | --- |
| 一、场景文档范围 | 各专业规程只在本场景内被引用 | `retrieval.scene_docs` | 输电缺陷不会引用《植保作业指引》的通用报告条款 |
| 二、条件分支校验 | 条件说的不是当前缺陷时，该句不抽为动作 | 条款原文中的条件引导词与后果类动词 | 金具锈蚀不照搬「出现裂纹、变形或磨损的，应按危急缺陷流程处理，立即申请停电更换」——那会是一次不必要的停电；被跳过的条件会在结论里点名 |
| 三、引用角色分离 | 命中但没成为动作的条款仍保留，标为参考 | `role=basis` / `role=reference` | 火情工单的依据是 3.1.1／3.2.3，而「一级／二级响应」判据以 `role=reference` 呈现，让人能核对 P1 是怎么判出来的 |

（出处：README 第五节「范围控制」）

### 4.5.1 场景文档范围的配置

【事实】`config/app.yaml:46-49`：

| 场景 | 允许引用的文档 |
| --- | --- |
| `power` | `demo_line_guide` |
| `agriculture` | `demo_crop_guide` |
| `emergency` | `demo_emergency_plan`、`demo_line_guide` |

配置文件注释说明两件事：「留空或删掉某场景 = 该场景不限制；知识库页的自由检索始终是全库」。被范围排除的条款会在检索响应里以 `scope_excluded` 字段显式返回，而不是静默丢弃。【事实】

### 4.5.2 条件分支校验的两个踩坑

【事实】这两条来自 README 第九节，都已各留一条回归测试：

- **单字情态词必须带前后顾断言**：`应` 要挡「响应／供应／相应／应用／应对」，`按` 要限定成「按…执行／办理／规定」这类口径。否则「二级响应：……」「按季度盘点」都会被当成处置动作抽进工单。
- **条件分支的引导动词要含后果类**：「异物**已导致**放电痕迹或灼伤的，应立即申请停电清除」里的条件不是由「出现／发现」引出的，只认前半类动词会漏判，于是后果分支被当成当前动作。因此引导词表补入 `导致|造成|引发|产生`。

【判断】这两条是本项目「条件分支闸门」真正的工程内容。它的难点不是设计一个规则，而是发现规则在自然语言里的漏口——而每一个漏口被发现，都意味着此前有一条错误动作被抽进了工单。因此三条闸门都配了回归测试（README 第十一节「已完成（本轮）」）。【事实】

## 4.6 拒答：阈值 0.18 的来历与两类拒答

### 4.6.1 阈值从哪来

【事实】`config/app.yaml:26`：「`min_relevance: 0.18` — 融合后最高分低于此值 → 判定「知识库未覆盖」并拒答，禁止自由发挥」。

【实测】这个值的来历是一次反直觉的实测结论，写在 README 第七节 7.1 与 `docs/proposal/10_compliance.md`：改写题里**正确条款与错误条款的绝对分区间是重叠的（0.135 ~ 0.362）**，不存在一个能把两者分开的阈值。评测报告附录 A 提供了这道结论的逐题依据（例如 H-04「塑料膜挂到线上了 怎么办」在本系统下命中排名 1，而 H-09「拍回来的照片能不能压小了再存」在内 5 组配置里有 3 组命中排名在 5 名之外）。

【判断】由此得到两条结论，本项目选择的是第二条：

1. **不能靠降阈值提高命中率。** 把阈值降到 0.135 以下，被放进工单的错误条款数量会增加，而且**错误无法被分数本身暴露**——分数低不代表是错的，分数高也不代表是对的。
2. **正确条款但分数低于阈值时，选择拒答。** 在电力场景里，一条错误建议的代价（无谓停电、或按错误依据处置）远高于一条「我不知道」的代价。宁可少答，不可错答。

【判断】必须承认这个选择的代价：拒答会带来漏判风险。当前系统对漏判的处理是**把条目全部转人工复核**，而不是放宽阈值（该责任划分见第十章）。

### 4.6.2 两类拒答要分开

【实测】8 道越界题拒答率 100%（评测报告第 3 节）。但其中 4 道**边界题**被拒的原因不是分数低：

| 编号 | 问题 | 最高分 | 最近条款 |
| --- | --- | --- | --- |
| X-04 | 红外测温的温升判据是多少 | 0.2629 | `demo_line_guide:1.1.2` |
| X-05 | 直升机巡检的作业间隔要求 | 0.4881 | `demo_line_guide:1.1.2` |
| X-06 | 农药配比怎么计算 | 0.3712 | `demo_crop_guide:1.1.2` |
| X-07 | 带电作业现场操作票怎么填写 | 0.5342 | `demo_line_guide:1.1.2` |

四道题的最近条款恰好是**文档自己的范围排除声明**（「本导则不适用于……」），分数从 0.2629 到 0.5342，**全部高于 0.18**——靠阈值拦不住。【实测】

因此系统区分两类拒答：

- `scope_excluded = true`：「超出知识库覆盖范围」——最相似条款本身是排除声明；
- 分数不够：「知识库未覆盖」——最高分低于阈值。

【事实】前端两种文案分开显示，因为这两种情况对用户的含义完全不同（README 第七节 7.2）。【判断】同理，空查询不进入这条链路：`POST /api/search` 对空查询返回 422，因为「没问问题」与「知识库没覆盖」是两回事，前者不该被渲染成后者（`loweye/api.py:52-69`）。【事实】

## 4.7 SAHI 切片：为小目标做的推理改造

【事实】航拍绝缘子缺陷在原图里往往只有几十像素，整幅缩放到 640 必然漏检。本项目按 SAHI 思路实现「切片推理 + 跨切片去重」：把原图切成带重叠的瓦片，逐片推理，再把各片的框映射回原图坐标去重（`loweye/detect/slicing.py`，104 行）。

| 函数 | 职责 | 关键参数 |
| --- | --- | --- |
| `compute_starts(total, size, stride)` | 给定边长、切片边长、步长，返回切片起点；**末尾强制补上 `total - size`**，避免右/下边缘被裁掉 | 步长 `stride = round(size × (1 - overlap))` |
| `slice_image(w, h, size, overlap)` | 切成覆盖全图的瓦片，`overlap` 必须落在 [0, 1) | `detect.slice.size: 640`、`detect.slice.overlap: 0.2`（`config/app.yaml:63-66`） |
| `nms(detections, iou_threshold)` | **按类别**做贪心 NMS，合并重叠区里重复检出的同一目标 | `detect.nms_iou: 0.50`（`config/app.yaml:57`） |
| `offset_boxes(detections, tile)` | 把切片内坐标映射回原图坐标，并打上 `slice_id: tileN` 标记 | 映射后按切片边界裁剪 |

【判断】这台模块有三个设计选择值得说明：

1. **按类别做 NMS，而不是全局 NMS。** 一个绝缘子自爆框与一个金具锈蚀框位置接近是正常的（同一基杆塔的两个缺陷），全局 NMS 会把其中一个消掉。因此去重只在同类之间进行。【事实】
2. **切片起点补边界，而不是丢弃边缘残片。** 只按 `range(0, total-size+1, stride)` 取起点，会漏掉最右/最下一条带；补上 `total - size` 后覆盖完整，代价是最后两个切片重叠度更高——由 NMS 处理。【事实】
3. **纯函数实现，与模型无关。** 因此可以用假检测器做单元测试：切片边界、坐标映射、跨片去重这三件事被验证过，而不是「应该没问题」（`loweye/detect/slicing.py:7-8`）。【事实】

【事实】切片本身在执行时也会被记录：`pipeline.py` 把实际切片数写回检测结果（`slice_count` 字段），并在检测器给出警告时生成 `Degradation(stage="detect", fallback="本次按空检测结果继续")`。

【待核实】切片当前只在 sidecar 回放下跑通了流程，**没有在真实权重上测过小目标召回增益**。因此本章不给出「切片把 mAP 提高了多少」这类数字——那需要在真实标注集上做切片/不切片对照，属于 README 第十一节「下一步」的第 2 项。【判断】

## 4.8 降级链与 degradations

### 4.8.1 五条降级路径

| 环节 | 首选 | 失败时 | 触发条件 |
| --- | --- | --- | --- |
| 检测 | ONNX + 切片 | sidecar 回放 → 空检测器 | 缺权重 / 缺 onnxruntime（`detect.onnx_path: null`） |
| 向量 | sentence-transformers（BGE-M3） | hashing_tfidf（零下载、确定性） | 未安装或缺权重；降级原因文案由 `loweye/retrieval/embedder.py:145` 生成 |
| 重排 | cross-encoder（bge-reranker-v2-m3） | 词法重排 | 未安装；词法重排的优势是绝对分不随批次归一化 |
| 生成 | 云端 OpenAI 兼容接口 | template 后端 | 超时 / 失败（`timeout_s: 20`、`max_retries: 1`） |
| 检索 | 向量 + BM25 | 仅 BM25 | 向量库不可用 |

（出处：README 第五节「降级链」）

### 4.8.2 降级是可观测的一等输出

【事实】降级不是异常处理，而是结果结构里的一个字段。`Degradation` 有三个必填部分：`stage`、`reason`、`fallback`。阶段名是枚举的：

| stage | 何时产生 | fallback 文案 | 出处 |
| --- | --- | --- | --- |
| `bootstrap` | 构建流水线时后端初始化失败（知识库为空、检测器/生成器降级） | 系统按降级后的后端继续运行 | `pipeline.py:150-152` |
| `detect` | 检测器返回警告 | 本次按空检测结果继续 | `pipeline.py:161-162` |
| `retrieve` | 检索环节报告降级 | — | `pipeline.py:236-238` |
| `generate` | 生成后端降级 | 使用 {generator} 生成 | `pipeline.py:198-200` |
| `dispatch` | 工单落库失败 | 工单仅在内存中保留 | `pipeline.py:291-292` |
| `notify` | 通知发送失败 | 通知未送达，工单仍已落库 | `pipeline.py:298-299` |

【判断】`fallback` 这个字段是这个设计里最有用的一格：它回答的不是「哪里坏了」，而是「坏了以后这次的结论还成不成立」。`dispatch` 的 fallback 明说工单只在内存里（刷新就没了），`notify` 的 fallback 明说通知没发但工单已落库——**两者的严重程度完全不同，界面上也分开显示**。

【事实】降级同时出现在三个地方：API 响应（`/api/health` 的 `warnings`、`/api/kb/stats` 的 `degradations`）、归档快照（`out/traces/{trace_id}.json`）、PDF 报告的「降级项」一节。**任何一步降级都不会被吞掉**，这是 `loweye/api.py:3-6` 写在接口设计原则里的第二条。

【判断】这条对本项目格外重要，因为当前**默认运行状态本身就是降级的**：检测器是 sidecar（无权重）、向量是 hashing_tfidf（非神经网络）、重排是词法。如果降级不可见，读者会把「链路跑通」误读成「模型可用」。让降级可见，等于让口径自己守住自己。

## 4.9 实测时延与预算

【实测】评测报告第 4 节，测试条件为本机 CPU、无 GPU：

【判断】这组数字说明的是**决策层本身的开销很小**：端到端 P95 的 24.4 ms 里，绝大部分来自 `detect`（18.33 ms），而当前 `detect` 是读 sidecar 文件，不是推理。因此：

- 「检索 + 分级 + 派单 + 归档」这段自研链路的 P95 约为 10 ms 量级（24.4 − 18.33 ≈ 6 ms，加上 `archive` 的 0 ms）。【推导】

## 4.11 本章结论

1. **四层架构的判据是依赖方向**：数据层（配置文件）不依赖任何业务代码，能力层四个后端可插拔且接口一致，编排层是唯一知道整条业务的地方，应用层只消费结构化结果。【事实】
2. **编排选显式状态机而不是 ReAct 循环**：流程本身是确定的，四个阶段键固定，降级的六个阶段名可枚举；自由循环能「决定」的部分恰好是本项目认为不该由模型决定的部分。【判断】
3. **分级不交给大模型**：10 条规则的等级、时限、岗位写在 `config/routes.yaml`，4 个条件触发人工复核，P1 一律人工确认后才派单。【事实】
4. **默认模板生成是结构保证**：模板后端没有生成新条款号的代码路径，因此「引用不存在的条款」不可达——这是「可溯源率 100%」是结构结论而不是精度结论的原因。【判断】
5. **检索链路的参数全部落在配置文件**：BM25 30 + 向量 30 → RRF(k=60) 取 20 → 词法重排 → top-5，覆盖阈值 0.18，引用强制带条款号。【事实】
6. **拒答阈值 0.18 不是调出来的，是实测逼出来的**：改写题正确/错误条款绝对分区间重叠（0.135~0.362），因此选择拒答而不降阈值；系统区分「超出覆盖范围（scope_excluded）」与「分数不够」两类拒答。【实测】
7. **三道闸门只作用于生成动作的链路**，自由检索不受限；两处已发现的自然语言漏口（单字情态词、后果类引导动词）各配一条回归测试。【事实】
8. **降级是结果的一部分**，六个阶段名 + reason + fallback 三字段结构化记录，同时出现在接口响应、归档快照与 PDF 报告三处。【事实】
9. **时延结论只在当前后端下成立**：端到端 P95 24.4 ms 中 18.33 ms 来自读 sidecar 的检测环节；换成真实 ONNX 推理后必须重测，本项目不把当前数字当作系统时延对外主张。【实测 + 判断】
